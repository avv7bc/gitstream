# Частичный stage отдельных строк — дизайн

Дата: 2026-05-17

## Контекст

Дорожная карта (CLAUDE.md) устарела: коммит `8acea87` реализовал пункты 1–6
**на уровне хунков** (Stage/Unstage/Discard целого хунка в `SideBySideDiffView`).
Незавершённая часть приоритетного пункта №1 — stage/unstage/discard
**отдельных строк** (выделение диапазона строк внутри/между хунками).

Текущая инфраструктура, которая переиспользуется без изменений:

- `mutation::apply_patch(repo_path, patch, reverse, cached)` — применяет
  unified-патч через `git apply`.
- Команды `stage_hunk`/`unstage_hunk`/`discard_hunk` строят патч из
  `file_header + hunk.raw` и зовут `apply_patch`.
- Diff отображается единственным режимом — `SideBySideDiffView.vue`
  (unified-режим в проект не подключён).
- `useDiff.diffContext` ∈ `unstaged | staged | commit` — определяет доступные
  операции. `useFiles.applyHunk` делает `refresh()` + `reloadDiff()`.
- Sequence-guard от гонок уже есть в `useDiff`/`useFiles`.

## Решение

Подход **A**: синтез частичного патча выполняется в Rust (тестируемо,
переиспользует `apply_patch`). Фронтенд лишь собирает выделение и передаёт
сырые хунки + порядковые номера выбранных изменённых строк.

## 1. Архитектура и поток данных

Состояние выделения — локальный `ref` в `SideBySideDiffView.vue`.
Существующие кнопки Stage/Unstage/Discard в шапке панели:

- если есть активное выделение строк → действуют на **выбранные строки**
  (новая команда `apply_lines`);
- если выделения нет → действуют на хунк целиком (текущее поведение,
  команды `stage_hunk`/`unstage_hunk`/`discard_hunk` без изменений).

Поток для строк:

```
SideBySideDiffView (выделение)
  → useFiles.applyLines(op, selection)
  → invoke("apply_lines", { repoPath, fileHeader, hunks: [{ raw, lines: [ord...] }], op })
  → commands::apply_lines
  → mutation::apply_lines  (синтез патча + apply_patch)
  → refresh() + reloadDiff()
```

## 2. Бэкенд: синтез патча (`mutation::apply_lines`)

Сигнатура (Rust):

```rust
pub struct LineHunkSelection {
    pub raw: String,            // сырой текст хунка, включая строку @@
    pub selected: Vec<usize>,   // 0-based порядковые номера изменённых
                                // (+/-) строк внутри тела хунка
}

pub fn apply_lines(
    repo_path: &Path,
    file_header: &str,
    hunks: &[LineHunkSelection],
    op: LineOp,                 // Stage | Unstage | Discard
) -> Result<(), GitError>
```

Алгоритм для одного хунка. Идём по строкам тела (после строки `@@`),
ведём счётчики `old_count`, `new_count`; индекс `ord` инкрементируется
только на `+`/`-` строках:

| Строка | Выбрана | Действие | old | new |
|--------|---------|----------|-----|-----|
| `' '` контекст | — | оставить `' '` | +1 | +1 |
| `'-'` | да | оставить `'-'` | +1 | — |
| `'-'` | нет | заменить на `' '` | +1 | +1 |
| `'+'` | да | оставить `'+'` | — | +1 |
| `'+'` | нет | выбросить строку | — | — |
| `'\ No newline at end of file'` | — | перенести, если предыдущая сохранённая строка осталась | — | — |

Новый заголовок: `@@ -<old_start>,<old_count> +<new_start>,<new_count> @@`
(плюс возможный текст после `@@`, который сохраняем как есть).
`old_start`/`new_start` берутся из исходного заголовка без изменений.
Особый случай счётчика: если count == 0, git пишет `-<start>,0` /
`+<start>,0` — сохраняем это поведение (формируем `,0`, start не
декрементируем — git-apply это принимает для пустых сторон; на практике при
наших трансформациях пустых сторон не возникает, т.к. контекст всегда
остаётся, но обрабатываем формально).

Хунк, в котором после трансформации не осталось ни одной `+`/`-` строки
(ничего не выбрано в этом хунке) — **пропускается целиком**.

Итоговый патч: `file_header` + конкатенация непустых пересобранных хунков.
Если все хунки пусты — возврат `Ok(())` без вызова git (нечего делать).

Маппинг `op` → флаги `apply_patch` (источник диффа — на стороне фронта:
для Stage/Discard передаётся unstaged-дифф, для Unstage — staged-дифф):

| op | reverse | cached | git |
|----|---------|--------|-----|
| Stage   | false | true  | `git apply --cached` |
| Unstage | true  | true  | `git apply --cached --reverse` |
| Discard | true  | false | `git apply --reverse` |

Семантика совпадает с `git gui` / `git add -p` (line staging).

Команда `commands::apply_lines` — тонкая обёртка
(`Path::new`, `map_err(|e| e.to_string())`), регистрируется в `main.rs`.

## 3. Фронтенд: выделение строк

В `SideBySideDiffView.vue`:

- Выделяемы только изменённые строки (`kind === 'added' | 'removed'`).
  Контекстные строки кликом не выделяются.
- **Клик** по строке — выделить только её, сделать якорем.
- **Shift-клик** — выделить диапазон от якоря до текущей (по порядку строк
  в плоском списке всех изменённых строк файла; диапазон может пересекать
  границы хунков).
- **Ctrl/Cmd-клик** — переключить одну строку, не сбрасывая остальные;
  обновить якорь.
- Подсветка выбранных строк — фоновый акцент (новый CSS-класс,
  отличимый от `added`/`removed`).
- Выделение сбрасывается при: смене файла, смене `diffContext`,
  успешном применении операции (после `reloadDiff`).
- Идентификатор строки — `(hunkIdx, lineIdxInHunkLines)`; для бэкенда
  выделение конвертируется в `selected` (порядковые номера среди
  `+`/`-` строк тела хунка, в порядке `hunk.lines`).

Кнопки в шапке (`diffContext`-зависимые, как сейчас):

- `unstaged`: **Stage** и **Discard** — при выделении применяются к
  выбранным строкам; Discard проходит через существующий `ConfirmDialog`
  (разрушающая операция, текст уточняет «N выбранных строк»).
- `staged`: **Unstage** — к выбранным строкам.
- `commit`: операции недоступны (как сейчас).

Опционально (не блокирует MVP, оставляем на усмотрение реализации):
счётчик «выбрано N строк» рядом с кнопками.

`useFiles`: добавить `applyLines(op, selection)` по аналогии с `applyHunk`
(`invoke("apply_lines", …)` → `refresh()` + `reloadDiff()`).

## 4. Обработка ошибок и крайние случаи

- `git apply` отклонил патч (контекст не сошёлся, файл изменился) →
  существующая `classify_git_error` → тост; дифф перечитывается
  (`reloadDiff`), выделение сбрасывается.
- Пустое выделение → кнопки работают по хунку (поведение без изменений).
- `\ No newline at end of file` — переносится со своей строкой только если
  та сохранена; покрыто тестом.
- CRLF / смешанные окончания — патч строится из сырого текста хунка
  байт-в-байт, переносы строк не нормализуются.
- Бинарные файлы — у хунков нет текстовых строк; выделение недоступно.
- Мульти-хунк выделение — каждый хунк трансформируется независимо,
  пустые отбрасываются.
- Гонки быстрых кликов/смены файла — покрыты существующим sequence-guard
  в `useDiff`/`useFiles`.

## 5. Тестирование

Rust-юнит-тесты рядом с существующими в `mutation.rs`
(`#[cfg(test)]`), на чистую функцию синтеза патча (без вызова git):

1. Смешанный хунк, выбрано подмножество `+` и `-`.
2. Выбраны только добавления (`+`).
3. Выбраны только удаления (`-`).
4. Невыбранные `+` выбрасываются, невыбранные `-` → контекст;
   корректный пересчёт `@@`.
5. `\ No newline at end of file` на сохранённой/несохранённой строке.
6. Мульти-хунк: один хунк с выбором, второй пустой → во втором хунк
   отброшен.
7. Пустой результат (ничего не выбрано во всех хунках) → патч не
   формируется.
8. Заголовок с текстом после `@@` (имя функции) сохраняется.

Проверки перед завершением: `cargo build` + `cargo test` (src-tauri),
`npm run build`, ручная проверка stage/unstage/discard строк в трёх
контекстах, бамп patch-версии в заголовке «GitStream v0.1.x».
